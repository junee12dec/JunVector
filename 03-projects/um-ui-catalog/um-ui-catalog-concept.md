# UM 과제 UI 카탈로그화 — 개념 설계

> 출발점: [[doksam-ui-shadcn-korean-ui-standard-catalog|doksam-ui]] (shadcn/ui 기반 컴포넌트·패턴·템플릿 카탈로그, 라이브 https://ui.doksam.com) 딥다이브 (2026-11-19)
> 근거: doksam-ui README와 대화. 사내 자산(Confluence·포털·레포)은 직접 보지 않았다.

## 목적

**개발자가 정립하고, AI 에이전트가 쓸 수 있게 해서 결과 품질과 자동화를 구축한다.**

- 사람: 표준을 정하고, 에이전트가 찾아 준 충돌을 판정하고, 항목을 승인한다
- 에이전트: 승인된 카탈로그만 근거로 Vue 화면을 만들고, 검사 규칙을 통과해야 끝낸다

## 1. 층 구조 (doksam-ui의 뼈대에 사내 자산을 대응)

| 층 | 역할 | 사내 자산 |
|---|---|---|
| 토큰 | 색·간격·글자 값 | DSDS(사내 디자인) |
| 기본 컴포넌트 | 무엇을 쓰나 | Vuetify |
| 조합 컴포넌트 | 사내 공통 부품 | MSDL(사내 웹 프레임워크) |
| 패턴 | 어떻게 조합하나 | 레이아웃 표준, 패턴 |
| 템플릿 | 완성 화면 | FDC 골든템플릿 |
| 규칙 (한 곳에만) | 판단 기준 | 디자인 표준 |

- 카탈로그의 가치는 흩어진 자산을 "이 화면 → 이 템플릿 → 이 패턴 → 이 컴포넌트"로 한 줄로 잇는 것이다.
- **doksam-ui와 다른 점**: shadcn은 컴포넌트 소스를 프로젝트에 복사해 넣는 방식이라 컴포넌트를 바로 "설치"할 수 있다. Vuetify·MSDL은 라이브러리로 가져다 쓰므로, 사내 카탈로그에서 설치에 해당하는 것은 **패턴·템플릿의 코드 조각**이다. 무게중심이 컴포넌트가 아니라 패턴·템플릿 층에 있다.

## 2. 항목 하나가 갖는 세 가지 형태

에이전트에게 읽히는 것만으로는 긴 작업 중 규칙을 놓친다. 사람이 리뷰로 막던 것을 기계 검사로 바꿔야 자동화가 된다.

| 형태 | 쓰는 쪽 | 예 (FDC 조회 화면 템플릿) |
|---|---|---|
| **보는 문서** | 개발자 | 데모, 코드, Do/Don't, 언제 쓰는지 |
| **읽는 색인** | 에이전트 | `llms.txt`와 항목별 짧은 md: "조회 조건 + 그리드 + 상세 화면이면 이 템플릿, 쓰는 MSDL 컴포넌트는 이것" |
| **검사 규칙** | 에이전트·CI | DSDS에 없는 색 금지, 레이아웃 표준의 여백 단위만 허용, Vuetify를 직접 쓰지 않고 MSDL 래퍼를 쓰는지 |

결과 품질은 세 번째가 지킨다. 에이전트가 만든 화면이 검사를 통과해야 끝나므로 사람이 매번 리뷰하지 않아도 된다.

## 3. 원본별 역할 분담 — "값은 코드에서, 이유는 문서에서"

| 원본 | 믿을 수 있는 것 | 카탈로그에서 맡는 칸 | 근거 표기 |
|---|---|---|---|
| **GitHub 레포** (FDC 골든템플릿, MSDL, Vuetify 테마 설정) | 실제로 동작하는 값 | 토큰 값, 컴포넌트 props, 템플릿 코드. 코드에서 자동으로 뽑는다 | 커밋 |
| **Confluence** (디자인 표준, 레이아웃 표준) | 왜·언제 쓰는지 | 규칙, Do/Don't, 쓰는 상황. 에이전트가 초안, 개발자가 승인 | 페이지 제목 + 수정일 |
| **포털** (DSDS로 가정) | 보이는 모습의 기준 | 시각 기준, 스크린샷 비교 | 페이지 + 확인일 |

## 4. 충돌 처리 — 코드 기준

**문서와 코드가 다르면 코드를 따르되, 차이는 버리지 않고 남긴다.**
- 예: Confluence 8px, 코드 12px → 카탈로그에는 12px, "Confluence 레이아웃 표준 갱신 필요"를 목록에 남긴다.
- 사람이 Confluence를 보고 일해도 틀리지 않게 하고, 나중에 12px이 실수로 판정되면 되돌릴 근거가 된다.

**코드끼리 다를 때의 신뢰 순서**
1. FDC 골든템플릿 — 의도적으로 만든 기준
2. MSDL — 공통 프레임워크로 배포된 구현
3. DSDS 토큰·Vuetify 테마 설정 — 값의 원천
4. 이미 전환된 업무 화면 — 참고만 한다. 여기서 나온 차이는 "이 화면이 표준을 벗어났다"로 기록한다

→ 검사 규칙을 기존 화면에 돌리면 **표준을 벗어난 화면 목록**이 덤으로 나온다.

**"개발자가 정립한다"의 실제 모습**: 에이전트가 찾아 준 불일치 목록을 하나씩 판정하고 항목을 승인하는 일.

## 5. madi와 맞닿는 지점

- **승인 흐름**: madi는 에이전트가 `draft`로 쓰고 사람만 `approved`로 바꾼다 → 카탈로그 항목도 같은 흐름. 에이전트는 approved 항목만 근거로 쓴다.
- **기계 검사**: madi의 `garalint`처럼 검사 규칙을 스크립트로 둔다.
- **변경 감지**: 근거에 커밋·수정일을 남기면 레포나 Confluence가 바뀔 때 해당 항목을 `stale`로 표시해, 표준은 바뀌었는데 카탈로그만 옛것으로 남는 문제를 막는다.
- 관련 탐구: [[dr-dci-agentic-search-dynamic-workspace-expansion|DR-DCI 딥다이브]] (madi의 근거 관리·변경 감지 설계)

## 남은 질문

- 카탈로그를 madi의 새 도메인으로 둘지, 별도 저장소·사이트로 둘지
- WPF 화면 유형 → 카탈로그 템플릿·패턴 대응표를 어떻게 만들지 (전환 작업에서 에이전트가 가장 먼저 찾을 연결)
- 검사 규칙을 무엇으로 구현할지 (ESLint 규칙, stylelint, madi lint 스크립트)
- Confluence·포털을 에이전트가 읽는 경로 (내보내기 파일로 `raw/`에 넣을지)
- 포털이 정확히 무엇을 담고 있는지 확인 (지금은 DSDS 가이드로 가정)
