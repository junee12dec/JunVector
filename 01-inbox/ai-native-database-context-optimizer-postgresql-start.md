# AI-Native DB와 Context Optimizer

@richardlee0202 (Threads, 2026-11-27, "오늘의 개발자 생각"). 본문과 작성자 댓글, 첨부 인포그래픽(8칸)을 합쳐 정리했다. 주장과 의견 글이며 구현이나 벤치마크는 없다.

## 핵심 주장

AI에게 필요한 것은 단순한 데이터 조회가 아니다.

- 데이터의 의미와 관계 파악
- 과거의 성공·실패 경험 기억
- 지식의 최신성과 신뢰성 확인
- 판단에 필요한 문맥 구성
- 토큰 사용량과 검색 비용 최적화

**벡터 DB만으로는 이 모든 문제를 풀기 어렵다.** 그래서 기존 Query Optimizer(데이터를 빠르게 가져오기)와 별개로, AI가 정확히 판단하는 데 필요한 정보를 선별하는 **Context Optimizer**가 중요해질 것이라고 본다.

**시작은 작게**: 새 DB 엔진을 만들 필요 없이, PostgreSQL을 기반으로 벡터 검색·지식 그래프·경험 저장·출처 검증을 통합하는 AI 전용 데이터 계층부터 만든다.

댓글: "LLM이 AI의 추론 엔진이라면, AI-Native Database는 AI의 기억과 지식을 관리하는 기반 시스템이다. AI 모델을 발전시키는 것만큼 AI가 쓸 데이터베이스를 발전시키는 것도 중요하지 않을까." 개발자에게 새로운 기회가 될 수 있다고 본다.

## 인포그래픽 내용

**기존 DB vs AI 중심 DB**

| 구분 | 기존 DB (인간 중심) | AI-Native DB |
|------|--------------------|--------------|
| 저장 대상 | 데이터 | 데이터·지식·경험 |
| 검색 방식 | SQL, 조건 검색 | 조건·의미·관계 검색 |
| 데이터 구조 | 사전 정의된 스키마 | 스키마 + 동적 지식 구조 |
| 관계 처리 | 명시적 관계 | 명시적 + 추론된 관계 |
| 시간 관리 | 생성·수정 시점 | 지식의 유효기간과 변화 |
| 신뢰성 | 데이터 정합성 | 정합성·출처·검증 상태 |
| 기억 | 저장된 기록 | 작업 기억·장기 기억 |
| 최적화 기준 | 조회 및 처리 성능 | 조회 성능·문맥 구성·토큰 비용 |

**아키텍처**: AI Agent/LLM(추론·계획·실행) → AI DB 인터페이스(자연어·SQL·API·Tool Calling) → 통합 저장소 → 권한 관리·트랜잭션·감사 기록.
통합 저장소는 6가지로 구성한다: 정형 데이터, 지식 그래프, 벡터 메모리, 경험 메모리, 시간 기반 지식(Temporal), 출처·검증(Provenance). 그 위에 Context Optimizer(관련성·최신성·토큰 비용 최적화)가 있다.

**Context Optimizer의 흐름** (기존 Optimizer는 SQL 요청 → 최적 실행계획 선택 → 데이터 반환):
1. AI의 목표와 질문
2. 정보 탐색 전략 결정 (SQL·Vector·Graph·Memory 중 선택)
3. 관련성·신뢰성 검증 (출처·최신성·권한·모순 확인)
4. 최적의 Context 반환 (필요한 정보만, 적절한 토큰 비용으로)

**AI가 쓰는 데이터 유형 5가지**: 정형 데이터, 지식 그래프, 벡터 메모리, 경험/작업 기록(시도한 방법과 결과, 성공/실패), 출처·검증 정보(출처·신뢰도·검증 상태)

**활용 시나리오**: 개발 보조 Agent(코드·문서·이슈·과거 해결 방법 통합 검색), 운영·장애 대응 Agent(장애 이력·로그·원인·해결 과정 기반 대응), 업무 자동화 Agent(메일·발주서·계약서 같은 비정형 문서를 이해해 DB와 연계)

**비유로 든 기존 흐름**: Google MLGO(2020, LLVM 컴파일러 최적화에 머신러닝), DeepMind AlphaDev(2023, 강화학습으로 새 정렬 알고리즘), Meta CompilerGym(2021), Vector·Graph DB 확산(Milvus, Qdrant, Neo4j). 코드 생성 AI와 코드 최적화 AI처럼 데이터도 '저장·검색·지식화·검증'으로 역할이 나뉜다는 논지다.

**결론**: "LLM이 AI의 추론 엔진이라면, AI-Native DB는 AI의 기억과 지식을 담아 더 정확하고 빠르고 실용적인 판단을 가능하게 하는 기반 시스템이다."

## 읽을 때 주의

- 인포그래픽의 `AI-Native DB`와 `Context Optimizer`는 이미 정립된 제품이나 표준이 아니라 글쓴이의 제안 구조다.
- 비유로 든 연구(MLGO·AlphaDev·CompilerGym)는 컴파일러·알고리즘 최적화 사례이고, 데이터베이스 문맥 최적화의 근거는 아니다. 직접 확인하지 않았다.

## 내 볼트와 이어지는 점

- [[madi-rag-index-sync|madi RAG 계획]]이 풀려는 문제와 겹친다. 이 글의 **출처·검증, 최신성(시간 기반 지식)** 축은 madi의 `sources` 근거와 `status`(draft·approved·stale), "근거가 바뀌면 stale" 장치와 같은 생각이다.
- 이 글의 "벡터 DB만으로는 부족하다"는 madi RAG의 A(벡터 DB 도입)와 B(근거 변경 → 상태 갱신만) 선택에서 B 쪽의 근거로 읽을 수 있다. 다만 이 글은 주장이고, 위키 규모와 "근거 없음" 빈도로 판단한다는 madi RAG의 기준이 먼저다.
