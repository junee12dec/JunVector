# DR-DCI — 검색으로 작업 공간을 넓히고 셸 명령으로 증거를 확인하는 에이전트 검색

- 논문: *Dr-DCI: Scaling Direct Corpus Interaction via Dynamic Workspace Expansion* (arXiv 2606.14885, 2026-06)
- 저자: Yi Lu, Zhuofeng Li, Ping Nie, Haoxiang Zhang, Yuyu Zhang, Kai Zou, Wenhu Chen, Jimmy Lin, Dongfu Jiang, Yu Zhang (토론토대, 텍사스 A&M, 워털루대, UC 샌디에이고 등)
- 코드: https://github.com/EigenTom/DR-DCI

## 풀려는 문제

대규모 문서 집합을 에이전트가 검색할 때 두 방식에 각각 한계가 있다.

| 방식 | 장점 | 한계 |
|------|------|------|
| **검색기 인터페이스** (BM25, ColBERT 등) | 후보를 넓게 찾아 순위를 매긴다 | 증거를 순위 목록이나 잘린 문서로만 보여 줘서, 에이전트가 자료를 재구성하거나 여러 문서에 걸친 조건을 확인하기 어렵다 |
| **직접 탐색 (DCI, Direct Corpus Interaction)** | `rg`, `find`, `sed`, 범위를 정한 파일 읽기 같은 셸 명령으로 검색·필터·비교·검증을 자유롭게 한다 | 문서 집합 전체에 명령을 돌리면 규모가 커질수록 느려지고 불안정해진다 |

## 핵심 아이디어 — 동적 작업 공간 확장

- 에이전트는 비어 있거나 작은 작업 공간에서 시작한다.
- `pull(query, topK)`를 호출하면 숨겨진 전체 문서 집합에서 관련 문서를 검색해 작업 공간에 파일로 꺼내 놓는다.
- 그다음 작업 공간 안에서만 DCI 방식으로 셸 명령을 써서 증거를 찾고 확인한다.
- 작업 공간은 시간이 지나면서 커진다. **검색은 탐색 범위를 넓게 유지하고, DCI는 증거를 정확하게 가리는 일을 맡는다.**
- 즉 검색을 에이전트가 부를 수 있는 "작업 공간 넓히기" 행동 하나로 다룬다.

## 결과

- **BrowseComp-Plus**: 정확도 71.2%. 원래 DCI와 일부 기능을 뺀 변형보다 최대 8.3%p 높고, 도구 호출 수·실행 시간·추정 비용은 줄었다.
- **작업 공간을 유지한 채 컨텍스트를 초기화**하면 정확도가 73.3%로 더 오른다.
- **규모 확장**: 문서 10만 개에서 1천만 개까지 성능이 유지된다. 같은 조건에서 원래 DCI는 불안정해지고 BM25는 크게 떨어진다.
- **Wiki-18 QA** (문서 하나당 파일 하나, 2천만 개 규모): 6개 벤치마크 평균 63.0점으로, 검색 기반 방식과 학습된 검색 에이전트보다 높다.
- **성능을 가르는 요소** (ablation): 순위가 붙은 미리보기, 그리고 여러 문서를 오가는 DCI.

## 코드로 해 보기 (README 기준)

```bash
bash setup.sh            # 한 번에 설치 (uv sync + 번들된 Pi 코딩 에이전트 빌드)
cp .env.template .env    # OPENAI_API_KEY 또는 ANTHROPIC_API_KEY 설정

# 로컬 문서 폴더에 DCI 에이전트 돌리기
uv run dci-agent-lite --terminal --provider openai --model gpt-5.4-nano \
  --cwd "corpus/wiki_corpus" --extra-arg="--thinking high"
```

- 동적 작업 공간을 쓰려면 검색기 서버(FAISS·Pyserini 유틸리티 제공, 기본 `http://127.0.0.1:8002/retrieve`)를 먼저 띄운다.
- BrowseComp-Plus, BRIGHT, 위키피디아식 QA, OpenResearcher식 문서 집합용 실행 스크립트가 들어 있다.
- 타임아웃, 출력 자르기, 컨텍스트 관리, 작업 공간 캐시 같은 장시간 실행 옵션을 CLI 플래그와 환경 변수로 조정한다.

## Deep Dive

> 탐구 주제: DR-DCI의 핵심 철학을 사내 보안 환경(DB는 접근 가능, 엑셀·PPT·PDF 보안 문서는 에이전트가 읽지 못함)에 맞춰 madi 레포에 적용하기
> 탐구 날짜: 2026-11-17
> 근거: madi 레포의 `prd/architecture.md`, `core/ops/query.md`, scout 에이전트, `compound/ideas/`의 DB 관련 노트 3개와 대화. 사내 PC에서 직접 시험하지는 않았다.

### 핵심 인사이트

- **철학: 전체를 뒤지지 말고, 필요한 것만 작업 공간에 꺼내 정밀하게 확인한다.** `pull`은 무엇을 꺼낼지 고르는 문, DCI(셸 명령)는 꺼낸 것끼리 비교·검증하는 손이다. 성능을 가른 것은 꺼내기 전의 순위 미리보기와 여러 문서를 오가는 확인이었다.
- **madi에서는 규모가 아니라 접근이 문제다.** 위키·코드는 작아서 `index.json`으로 고른 뒤 scout가 `rg`로 찾는 지금 방식이 이미 DCI다. 이 철학이 힘을 쓰는 곳은 에이전트가 직접 못 보는 원본(업무 DB의 행, 보안 문서)이고, 거기서 `pull`은 검색이 아니라 **보안 관문**이 된다. 무엇을·얼마나·어떤 컬럼을 빼고 꺼낼지가 한 지점에서 정해지고 기록된다.
- **DB 행은 질의별 작업 공간으로 꺼낸다.** `pull db <테이블> <조건>` 결과를 `outputs/ws/<질의-id>/`(Git 제외)에 개인정보 컬럼을 빼고 20행 이하로 파일로 꺼내면, 테이블끼리 `rg`·`awk`로 대조할 수 있다. 끝나면 지우고, 긴 `/next` 작업은 컨텍스트를 초기화해도 작업 공간을 남겨 이어 간다.
- **보안 문서는 내용은 막혀도 겉모습(파일 이름·경로·수정일)은 보인다.** 에이전트가 파일 목록만 훑고 용어집 별칭과 맞춰 후보를 고른 뒤, 경로와 시트·열까지 담아 "이 부분을 붙여넣어 달라"고 요청한다. 사람의 일이 "어디 있는지 찾아 알려 주기"에서 "가리킨 파일 한 군데를 열어 붙여넣기"로 줄어든다.
- **같은 파일명에 덮어쓰는 방식이라 경로와 수정일 한 쌍으로 변경을 감지할 수 있다.** `sources`에 `doc: <문서 제목>@<수정일>`을 남기고, `/status`·`/next`가 목록을 다시 훑어 새로워진 문서의 페이지를 stale **후보**로 알린다. 열고 저장만 해도 날짜가 바뀌는 오탐이 있으니, 사람이 "변경 없음"이면 날짜만 갱신하고 바뀌었으면 다시 붙여넣는다.

### 새롭게 알게 된 것

처음에는 DR-DCI를 대규모 검색 성능 기법으로 봤지만, madi에서는 "볼 수 없는 원본을 어떻게 좁게, 기록되게 꺼내느냐"의 설계 원리로 읽힌다. 특히 보안 문서는 읽지 못해도 파일 목록만으로 **위치 찾기와 변경 감지**를 할 수 있어서, 사람의 수고를 필요한 한 군데로 좁히고 근거 관리는 코드와 같은 수준으로 올릴 수 있다는 점이 핵심이다.

### madi에 넣을 설계안

1. **문서 목록 `raw/<domain>/docs/_catalog.md`** (Git 제외): 파일 경로·이름·수정일. 사람이 발췌를 붙여넣어 답을 찾을 때마다 "이 파일의 이 시트가 이런 질문에 답했다"를 한 줄 더한다 (내용은 쓰지 않음). 쓰면서 쌓이는 목록이라, 다음 질문은 파일 이름 추측이 아니라 실제로 답했던 기록으로 후보를 고른다.
2. **query의 문서 요청 단계**: 위키에 근거가 없으면 목록에서 후보 파일을 골라 경로·시트·열을 담아 요청한다.
3. **근거 표기 `doc: <문서 제목>@<수정일>`**: `content/`에는 제목과 수정일만 쓴다. 경로·서버명은 `raw/`의 목록에만 둔다 (`prd/architecture.md` 7절 보안 규칙).
4. **문서 변경 감지**: `/status`·`/next`가 목록의 수정일을 비교해 stale 후보와 "다시 붙여넣을 곳"을 알린다. 목록에서 사라진 파일(이름 변경)도 함께 알린다.
5. **pull 기록**: DB·문서를 꺼낼 때마다 무엇을, 언제, 몇 행인지, 어떤 컬럼을 뺐는지 기록한다 (값은 쓰지 않음). "Receipts Only"를 꺼내는 행동까지 넓힌다.
6. **들이지 않을 것**: 임베딩 검색기 서버(FAISS 등). 지금 규모에서는 `index.json`과 용어집 `컬럼` 칸이 순위 미리보기 역할을 한다.

### 남은 질문

- OpenCode가 문서 폴더의 목록을 실제로 어떤 명령으로 읽을 수 있는가 (네트워크 드라이브에서 `find`·`dir`의 속도, 수정일이 정확히 나오는지)
- 파일 이름만으로 후보를 고를 때 적중률이 얼마나 되나. 목록이 쌓이기 전 초기에는 폴더 구조가 얼마나 도움이 되나
- DB 작업 공간 파일을 지우는 시점: 답변 직후인가, 세션 종료인가
- 이 설계를 madi의 `compound/ideas/`에 아이디어 노트로 올릴지
